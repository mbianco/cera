# ADR-001: CESM as a complex Tool, not a peer entity

**Status:** Accepted
**Date:** 2026-09-14
**Supersedes:** Domain model's original C2 (Model Execution)
**Spec references:** `resolutions.md` R1; `domain-model.md` C2
(collapsed); `invariants.md` INV-M1–M4 (renumbered as INV-T6–T9);
`cross-context/interactions.md` X5, X6, X9, X11 (subsumed)

## Context

The original domain model (`domain-model.md`) placed CESM in its own
bounded context (C2 — Model Execution) with a dedicated `Case`
aggregate, distinct from C1 (Tool Invocation). The rationale was
CESM's multi-step lifecycle (create → configure → build → submit →
monitor → post-process) and its long running times (hours to weeks),
which seemed qualitatively different from stateless CLI Tools like
CDO and NCO.

This created several problems:
- An entire bounded context (C2) existed for a single entity (CESM),
  with only 4 invariants (INV-M1–M4).
- Cross-context interactions X5 (C2↔C4), X6 (C2↔C3), X9 (C5↔C2),
  X11 (C7↔C2) were largely duplicative of X2 (C1↔C4), X3 (C1↔C3),
  X1 (C1↔C5), X10 (C7↔C1).
- The boundary between "tool" and "model" was not load-bearing for
  any feature. CESM's `case.submit` is fundamentally a ToolInvocation
  that happens to submit a SLURM Job.

The domain expert resolved this (R1): CESM is a Tool, not a peer
entity. C2 collapses into C1.

## Decision

CESM is a **Model Tool** subtype in C1 (Tool Invocation), not a peer
entity in its own bounded context. The `Case` aggregate moves to C1.
The Case lifecycle (create → configure → build → submit → monitor →
post-process) is a specialized ToolInvocation lifecycle, not a
separate context.

### Tool subtypes

| Subtype | Examples | Execution model | Lifecycle |
|---------|----------|-----------------|-----------|
| CLI Tool | CDO, NCO, opengrads (if approved) | Synchronous (login node) or parallel (SLURM) | Single invocation |
| Python Tool | healpy, ICON tools, zarr | Synchronous (in-process or subprocess) | Single invocation |
| Model Tool | CESM | Always parallel (SLURM) | Multi-step: create → configure → build → submit → monitor → post-process |

### Invariant renumbering

| Original | New | Short |
|----------|-----|-------|
| INV-M1 | INV-T6 | Submit requires built Case |
| INV-M2 | INV-T7 | One running Job per Case |
| INV-M3 | INV-T8 | Run length bounded by Wall Time |
| INV-M4 | INV-T9 | Output tree location known before submission |

### Interaction collapse

| Original | Subsumed by | Change |
|----------|-------------|--------|
| X5 (C2↔C4) | X2 (C1↔C4) | CESM case.submit is a specific case of parallel tool delegation |
| X6 (C2↔C3) | X3 (C1↔C3) | CESM output tree registration is a specific case of tool output registration |
| X9 (C5↔C2) | X1 (C1↔C5) | CESM env requirements are a specific case of tool env requirements |
| X11 (C7↔C2) | X10 (C7↔C1) | CESM Case lifecycle is a specific case of tool invocation |

## Consequences

**Positive:**
- Simpler architecture: 6 bounded contexts instead of 7.
- Fewer cross-context interactions: 9 instead of 14.
- The `tool-invocation` module handles all Tool execution uniformly,
  with CESM as a specialized lifecycle variant.
- Provenance, error handling, and exit code semantics are uniform
  across all Tools (including CESM).

**Negative:**
- The `tool-invocation` module is more complex: it must handle
  single-invocation CLI Tools, Python Tools, and multi-step CESM
  Cases.
- The Case lifecycle (create → configure → build → submit → monitor →
  post-process) requires a state machine within `tool-invocation`,
  which is more than what other Tools need.

**Neutral:**
- The `Case` entity remains an aggregate root, but it lives in C1
  rather than C2. Its invariants (INV-T6–T9) are enforced by the
  `tool-invocation` module.

## Alternatives

### Alternative A: CESM in its own bounded context (C2)
This was the original design. It kept CESM's complexity isolated in
C2, with a clean boundary between "tool" and "model." However, the
boundary was not load-bearing for any feature, and it created
duplicative cross-context interactions. The domain expert rejected
this (R1).

### Alternative B: CESM as a Workflow, not a Tool
In this model, each CESM step (configure, build, submit, monitor)
would be a WorkflowStep, and the "Case" would be a specialized
Workflow. This is rejected because:
- CESM's lifecycle is a domain concept with its own invariants
  (INV-T6–T9), not an orchestration concern.
- The Case aggregate has specific state transitions (CREATED →
  CONFIGURED → BUILT → SUBMITTED → RUNNING → COMPLETED/FAILED) that
  are not generalizable to all Workflows.
- Workflow is in C7 (Agent Interaction), which is a higher-level
  concept than C1 (Tool Invocation). Placing CESM in C7 would
  invert the dependency: the Agent would need to know CESM-specific
  details, violating bounded context boundaries.
