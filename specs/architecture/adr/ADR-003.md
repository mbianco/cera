# ADR-003: uenv-based Environment Management (not Lmod)

**Status:** Accepted
**Date:** 2026-09-14
**Spec references:** `resolutions.md` R9; `assumptions.md` A4
(updated); `invariants.md` INV-E1, INV-E2, INV-E3 (re-evaluated);
`features/environment-management.feature` (needs rewrite)

## Context

The original specification assumed the module system on Alps is
**Lmod** (Lua-based module system), using `module load`, `module
avail`, `module spider`, and `module purge`. The feature file
`environment-management.feature` has an `@lmod` tag and uses these
commands throughout. The invariant INV-E3 references `module avail`
for availability verification.

The domain expert corrected this (R9): **Alps uses uenv (user
environments), not Lmod.** uenv are squashfs mounts at prescribed
paths with the required dependencies. This is a fundamentally
different mechanism:

| Aspect | Lmod (original) | uenv (actual) |
|--------|-----------------|---------------|
| Loading | `module load <name>/<ver>` | uenv mount (squashfs at prescribed path) |
| Availability check | `module avail`, `module spider` | uenv registry/mount check |
| Conflict detection | soname-level (same `.so`, different version) | filesystem path-level (same `LD_LIBRARY_PATH` entry, different version) |
| Stacking | Lmod supports module stacking | uenv may be mountable simultaneously if complementary |
| Unloading | `module purge` | uenv unmount |

This is a significant change because:
1. Environment loading is mount-based, not `module load`.
2. Conflict detection is at the filesystem path level, not the
   soname level.
3. The architect must understand uenv's mount lifecycle and how the
   Agent loads a uenv before invoking a Tool.
4. INV-E1, INV-E2, INV-E3 must be re-evaluated for uenv semantics.

## Decision

### Environment is a uenv mount

An Environment is a set of active uenv mount paths in `PATH` and
`LD_LIBRARY_PATH`. The `environment-management` module uses uenv CLI
commands (via `dsh-adapter.SubprocessRunner`) to mount, unmount, and
query uenvs.

### INV-E1 re-evaluated: One active Environment per execution context

**Original:** At most one Environment is active in a given execution
context at a time. Loading a new Environment replaces, not merges
with, the prior one (unless the module system explicitly supports
stacking and the result is verified conflict-free).

**uenv:** Multiple uenvs **may** be mounted simultaneously if they
are complementary (no path conflicts). However, only one logical
Environment (the set of active mount paths in `PATH`/
`LD_LIBRARY_PATH`) is active at a time. If two uenvs have path
conflicts, the second load is rejected.

The invariant is preserved: the active Environment is a single
consistent stack. The difference is that "single stack" may be
composed of multiple complementary uenv mounts, rather than a single
`module load` operation.

### INV-E2 re-evaluated: Conflict detection before execution

**Original:** Environment conflicts (incompatible compiler versions,
conflicting MPI runtimes, conflicting library sonames) are detected
before a Tool runs, not at Tool runtime via a segfault or linker
error.

**uenv:** Conflict detection is at the **filesystem path level**,
not the soname level. Two uenvs conflict if they provide different
versions of the same library at paths that would both appear in
`LD_LIBRARY_PATH`, or the same binary at paths that would both
appear in `PATH`.

The invariant is preserved: conflicts are detected before execution.
The detection mechanism changes from soname comparison to path
comparison.

### INV-E3 re-evaluated: Module availability verified before load

**Original:** A Module's availability on the target system is
verified before it is loaded. The Agent must not attempt to load a
Module that does not exist on the host.

**uenv:** Availability is verified via the **uenv registry/mount
system**, not `module avail` or `module spider`. The
`environment-management` module exposes `checkUenvAvailability()`
which queries the uenv registry.

The invariant is preserved: availability is verified before load.
The verification mechanism changes from Lmod commands to uenv
registry queries.

### `Module` value object retained but reinterpreted

The `Module` value object (name, version, prefix) is retained as a
**uenv component descriptor**: a component within a uenv mount (e.g.,
a compiler, an MPI runtime), identified by its mount path and
version. The term "Module" in ubiquitous language is qualified: it
refers to a uenv component, not a Lmod module.

## Consequences

**Positive:**
- The `environment-management` module correctly models the actual
  system on Alps (uenv), not an incorrect assumption (Lmod).
- Conflict detection at the filesystem path level is potentially
  more precise than soname-level (uenv conflicts are about path
  collisions, which is the actual failure mode).
- Multiple complementary uenvs can be mounted simultaneously,
  potentially simplifying some workflows (e.g., a CDO uenv and a
  Python uenv that don't share paths).

**Negative:**
- The feature file `environment-management.feature` must be
  rewritten. All `module load`, `module avail`, `module spider`, and
  `module purge` commands must be replaced with uenv equivalents.
  This is a significant spec gap (escalated).
- The exact uenv CLI syntax (mount, unmount, list, query) is not
  documented in the specs. The architect must either request uenv
  documentation from the domain expert or make reasonable
  assumptions and flag them.
- Unit tests for `environment-management` must mock uenv commands
  instead of Lmod commands.

## Alternatives

### Alternative A: Keep Lmod as the implementation, add a uenv adapter later
This would mean the initial implementation uses `module load` /
`module avail` / `module spider` and the domain model treats the
module system as an abstraction. Rejected: R9 explicitly states Alps
uses uenv, not Lmod. The `module` commands are not the right
commands.

### Alternative B: Abstract over both Lmod and uenv
Design a `ModuleSystem` interface with implementations for Lmod and
uenv. Rejected: premature abstraction. Only uenv is in scope (R9).
A clean `EnvironmentService` interface is sufficient for testability
without a multi-backend abstraction.
