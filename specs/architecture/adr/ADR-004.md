# ADR-004: SLURM-only, defer scheduler abstraction

**Status:** Accepted
**Date:** 2026-09-14
**Spec references:** `resolutions.md` R8; `assumptions.md` U2
(resolved: deferred); `domain-model.md` C4; `ubiquitous-language.md`
Scheduler

## Context

The original domain model (`domain-model.md` C4) abstracted the
Scheduler: "Abstracted over multiple scheduler backends in
principle; SLURM is the only one in scope today." The
`ubiquitous-language.md` entry for Scheduler says: "The domain model
treats the Scheduler as an abstraction; other schedulers (PBS, LSF)
may be supported later."

This abstraction raised several open questions (`assumptions.md` U2,
originally `[CRITICAL]`):
- How different are PBS/LSF/Cray job lifecycle semantics?
- Are `sbatch` <-> `qsub`, `squeue` <-> `qstat`, `scancel` <->
  `qdel`, `sacct` <-> `qhist` output formats compatible enough?
- Can a common `ResourceRequest` abstraction capture all backends?
- Does INV-S1 (Scheduler authoritative) hold equally for PBS and LSF?

Designing and maintaining a multi-scheduler abstraction without a
confirmed second backend would be speculative work with real
maintenance cost: every SLURM-specific behavior (UNKNOWN state for
30 min, `sacct` reconciliation, `--exclude` for node failures) would
need a generic interface that may not fit future backends.

## Decision

**SLURM is the only scheduler.** The domain specs treat the
Scheduler as SLURM directly, not as an abstraction with multiple
backends.

### What this means for the `scheduling` module

- `JobState` is SLURM-specific: `PENDING | RUNNING | COMPLETED |
  FAILED | TIMEOUT | CANCELLED | OUT_OF_MEMORY | NODE_FAIL |
  UNKNOWN`.
- `ResourceRequest` is SLURM-specific: `nodes`, `coresPerNode`,
  `memory`, `wallTime`, `partition`, `qos` — matching SLURM's
  `sbatch` flags.
- The module uses `sbatch`, `squeue`, `scancel`, `sacct` directly
  (via `dsh-adapter`).
- The `SchedulingService` interface is clean and testable (mockable
  CLI), but its types are SLURM-specific.

### What this does NOT mean

- The `SchedulingService` interface is still defined as an
  interface, not a concrete class. This allows unit tests to mock
  the scheduler without running SLURM.
- If a second scheduler is needed in the future, a new ADR will be
  written to design the abstraction. The current types will not be
  retrofitted; they will be replaced or wrapped.
- `assumptions.md` U2 moves from `UNKNOWN [CRITICAL]` to
  `ACCEPTED (deferred)`.

## Consequences

**Positive:**
- No speculative abstraction. The `scheduling` module is simpler and
  more direct.
- SLURM-specific behaviors (UNKNOWN state, `sacct` reconciliation,
  `--exclude` suggestions, R13's 30-minute tolerance) are modeled
  as first-class, not squeezed through a generic interface.
- Faster implementation: no need to design and test a
  multi-scheduler abstraction that may never be used.

**Negative:**
- If a second scheduler is needed, the work to abstract will be
  larger than if the abstraction had been designed upfront.
- The `SchedulingService` interface uses SLURM-specific types
  (`JobState`, `ResourceRequest`, `Partition`, `QoS`) that may not
  map cleanly to other schedulers.
- `JobState` includes `UNKNOWN`, which is not a standard SLURM
  state but is needed for R13 (SLURM unavailability). A future
  scheduler may not have an equivalent.

## Alternatives

### Alternative A: Multi-scheduler abstraction now
Design a `Scheduler` interface with a `SLURMBackend` implementation.
Other backends (PBS, LSF) would be added later. Rejected: premature
abstraction (R8). No confirmed second backend. The abstraction would
be speculative and may not fit future needs.

### Alternative B: No interface, concrete class only
Implement `SchedulingService` as a concrete class with no interface.
Rejected: the interface is needed for testability (mockable CLI
without a real SLURM controller). The interface does not add
abstraction cost; it adds testability.
