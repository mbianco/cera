# ADR-005: dsh isolation layer

**Status:** Accepted
**Date:** 2026-09-14
**Spec references:** `assumptions.md` A1; `failure-modes.md` FM-X3;
`ubiquitous-language.md` dsh

## Context

cera is built on **dsh** (DeepSeek Harness), a TypeScript/Node agent
framework with an "everything-is-a-plugin" architecture via Cordis.
dsh provides extension points including `ctx.tools`, `ctx.shell`,
`ctx.subprocess`, `ctx.sandbox`, `ctx.fs`, `ctx.jobs`,
`ctx.commands`, `ctx.agentTeams`, and `ctx.webhookRuntime`.

dsh is in **developer preview** with breaking-change warnings
(`assumptions.md` A1, `[CRITICAL]`). Breaking changes between
versions are possible and expected. cera's plugin contracts depend
on dsh's extension points. A dsh upgrade could break cera's Tool
invocations, Environment management, Job submission, or filesystem
access — any of which would halt the system.

The failure mode FM-X3 (dsh framework breaking change) is classified
as `CRITICAL` / `fatal`: stop, pin to previous version, do not
upgrade without full test suite.

## Decision

Introduce a **`dsh-adapter` module** as the sole point of contact
between cera and dsh. No other cera module imports dsh directly.

### Adapter responsibilities

The `dsh-adapter` module provides stable TypeScript interfaces
wrapping each dsh extension point that cera uses:

| Adapter interface | dsh extension point | Used by |
|-------------------|---------------------|---------|
| `ShellExecutor` | `ctx.shell` | `tool-invocation` (CLI Tools) |
| `SubprocessRunner` | `ctx.subprocess` | `tool-invocation`, `scheduling`, `environment-management` |
| `SandboxRunner` | `ctx.sandbox` | `tool-invocation` (process confinement) |
| `FilesystemGateway` | `ctx.fs` | `data-management`, `provenance`, `environment-management` |
| `JobBackend` | `ctx.jobs` | `scheduling` |
| `ToolRegistry` | `ctx.tools` | `agent-interaction` (Actions) |
| `CommandRegistry` | `ctx.commands` | `agent-interaction` |

### Stable surface vs. volatile surface

The adapter exposes a **stable surface** (the interfaces above) that
cera's domain modules depend on. The adapter internally uses dsh's
**volatile surface** (the extension points themselves). When dsh
changes:

1. Only `dsh-adapter` needs to be updated.
2. cera's domain modules (scheduling, environment-management,
   provenance, data-management, tool-invocation, agent-interaction)
   do not need changes.
3. The full test suite (Tier 3) is run against real services before
   merging any dsh upgrade.

### Version pinning

The dsh version is pinned in `package.json` / lockfile. No
auto-updates. Upgrades are deliberate, reviewed, and tested.

## Consequences

**Positive:**
- cera's domain modules are insulated from dsh's volatility. A dsh
  breaking change requires updating one module (`dsh-adapter`),
  not six.
- The adapter interfaces are stable and documented, making it clear
  what cera needs from dsh (and what it doesn't).
- Unit tests for domain modules can mock the adapter interfaces
  without importing dsh, reducing test setup complexity.
- If dsh is ever replaced (unlikely but possible), only the adapter
  needs rewriting.

**Negative:**
- One extra module and one extra layer of indirection. Every dsh
  call goes through the adapter.
- The adapter must be kept in sync with dsh's API. If a dsh
  extension point changes shape, the adapter must be updated before
  any cera feature can use it.
- The adapter interfaces must be designed carefully: too thin and
  they leak dsh types; too thick and they duplicate dsh
  functionality.

## Alternatives

### Alternative A: Direct dsh imports (no adapter)
Each cera module imports dsh extension points directly. Simpler
initially, but a dsh breaking change would require updating all
modules simultaneously. Rejected: A1 explicitly recommends an
isolation layer.

### Alternative B: Code generation
Generate adapter code from dsh's type definitions automatically.
Rejected: premature. The adapter is small (7 interfaces) and benefits
from manual review. Code generation would add a build step and a
dependency on dsh's type system, which is itself volatile.

### Alternative C: Feature flags
Use feature flags to test new dsh versions alongside the old one.
Rejected: dsh is a framework, not a feature. Feature flags don't
help with API shape changes. Version pinning + full test suite is
sufficient.
