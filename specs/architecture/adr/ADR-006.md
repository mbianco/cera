# ADR-006: Workflow persistence model

**Status:** Accepted
**Date:** 2026-09-14
**Spec references:** `resolutions.md` R6; `assumptions.md` U5
(resolved: VALIDATED); `domain-model.md` C7, Workflow;
`invariants.md` INV-W1, INV-W2, INV-W4; `features/workflow-execution.feature`

## Context

The original domain model marked `WorkflowState` as `[CANDIDATE]`:
"NOT_STARTED | IN_PROGRESS | BLOCKED | COMPLETE | FAILED." The
analyst asked the domain expert whether Workflow is a first-class
entity with persisted state (surviving Session end) or an ephemeral
plan (recreated each Session) (`assumptions.md` U5, `[HIGH]`).

The feature file `workflow-execution.feature` assumed first-class
semantics (resume after Session, state transitions), but this was
an unconfirmed assumption.

The domain expert resolved this (R6): **Workflow is a first-class
entity with persisted state. A User can resume a Workflow across
Sessions ("continue the analysis I started yesterday").**

## Decision

Workflow has persisted state that survives Session end. The
`agent-interaction` module is responsible for persistence.

### Persistence model

The Workflow is persisted as a **JSON document on the filesystem**,
stored in a user-specific directory (e.g.,
`~/.cera/workflows/{workflowId}.json`). The document contains:

```json
{
  "id": "wf_...",
  "name": "annual_mean_workflow",
  "experimentId": "exp_...",
  "state": "IN_PROGRESS",
  "steps": [
    {
      "order": 1,
      "name": "select_tas",
      "toolId": "cdo",
      "parameters": { ... },
      "inputDatasetIds": ["ds_..."],
      "outputDatasetId": "ds_...",
      "executionModel": "synchronous",
      "state": "COMPLETED"
    },
    ...
  ],
  "createdAt": "2026-09-14T10:00:00Z",
  "updatedAt": "2026-09-14T10:30:00Z"
}
```

### Why filesystem, not database

- cera runs on HPC login/service nodes. A database server is an
  additional dependency that may not be available or desirable.
- The filesystem (Lustre, GPFS) is already a shared, persistent
  store that all Sessions on the same host can access.
- Workflow state is small (a few KB per Workflow). No need for a
  database's query or indexing capabilities.
- ProvenanceRecords (C6) are already filesystem-based. Using the
  same store for Workflow state keeps the persistence story simple.

### State transitions

```
NOT_STARTED → IN_PROGRESS → COMPLETE
                       ↘ → FAILED
                ↗ → BLOCKED → IN_PROGRESS (User resumes)
```

- `NOT_STARTED`: initial state after creation.
- `IN_PROGRESS`: at least one step is running or waiting to run.
- `BLOCKED`: a step cannot start because its input Datasets don't
  exist or lack Provenance (INV-W1), or because a predecessor step
  failed (INV-W2 — actually, failure leads to FAILED, not BLOCKED;
  BLOCKED is for input dependency issues).
- `COMPLETE`: all steps completed successfully.
- `FAILED`: a step failed and downstream steps are halted (INV-W2).

### Resume across Sessions

When a User starts a new Session and requests to resume a Workflow:

1. The `agent-interaction` module loads the Workflow JSON from the
   filesystem.
2. If a step is `IN_PROGRESS` and was waiting for a Job (submitted
   via `scheduling` in a previous Session), the Agent queries
   `scheduling.queryJob()` or `scheduling.queryJobsByUser()` for the
   Job's current state (R7: proactive reporting).
3. If the Job has reached a terminal state, the Workflow advances
   accordingly. If the Job is still running, the Workflow continues
   waiting.
4. The Workflow state is updated on the filesystem after each
   transition.

### What is NOT persisted

- The LLM's context for the Session (each Session starts with fresh
  context, per INV-W4's Session model).
- The loaded Environment (each Session must reload the uenv; the
  Environment identity is persisted in the ProvenanceRecord, but the
  mount does not persist across Sessions).
- ToolInvocation subprocess handles (processes from a previous
  Session are not accessible; only their outcomes, recorded in
  ProvenanceRecords and the filesystem, persist).

## Consequences

**Positive:**
- Users can resume Workflows across Sessions, matching their
  mental model ("continue the analysis I started yesterday").
- Workflow state is auditable: the JSON document records what was
  done, in what order, with what inputs and outputs.
- No additional infrastructure (database server) is required.
- Workflow persistence is consistent with Provenance persistence
  (both filesystem-based).

**Negative:**
- Filesystem JSON is not transactional. If the Agent crashes during
  a state transition, the JSON may be partially written. Mitigation:
  write to a temporary file and rename atomically (POSIX rename is
  atomic on the same filesystem).
- Concurrent Sessions modifying the same Workflow is not supported
  (out of scope per the original domain model's "cross-Session
  coordination is out of scope unless the domain expert requires
  it"). If two Sessions attempt to resume the same Workflow, the
  second should be rejected with a clear message.
- The Workflow JSON format is a cera-internal concern. If the
  format changes, a migration may be needed. Mitigation: include a
  `schemaVersion` field in the JSON.

## Alternatives

### Alternative A: Ephemeral Workflow (no persistence)
Each Session creates a Workflow plan from scratch. Individual
ToolInvocations and Jobs persist (via C1, C4, C6), but the Workflow
itself does not. Rejected by the domain expert (R6): scientists
need to resume Workflows across Sessions.

### Alternative B: Database persistence (SQLite)
Use SQLite for Workflow state. More robust than JSON (ACID, schema
enforcement). Rejected: adds a binary dependency (SQLite may not be
available on all HPC login nodes), and the data volume is small.
Filesystem JSON with atomic writes is sufficient.

### Alternative C: Store Workflow state in ProvenanceRecords
Model the Workflow as a series of ProvenanceRecords, one per step,
with a "workflow" field linking them. Rejected: ProvenanceRecords
are immutable and per-Dataset/per-Job. Workflow state (IN_PROGRESS,
BLOCKED) is mutable and per-Workflow, which doesn't fit the
ProvenanceRecord model. Also, querying "what is the state of
Workflow X?" would require scanning all ProvenanceRecords, which is
inefficient.
