# ADR-007: Proactive Job reporting on Session start

**Status:** Accepted
**Date:** 2026-09-14
**Spec references:** `resolutions.md` R7; `assumptions.md` U7
(resolved: VALIDATED, proactive); `cross-context/interactions.md`
X8; `invariants.md` INV-W4; `features/job-management.feature`,
`features/workflow-execution.feature`

## Context

A CESM run may last days to weeks. A Session (one interaction
between User and Agent) may end long before the CESM Job completes.
The Jobs are not cancelled when the Session ends (INV-W4). A later
Session can discover those Jobs by JobID.

The original cross-context interaction X8 (C4↔C7) documented this
discovery mechanism but left the **trigger** open: "Should the Agent
proactively report Job status when a new Session begins, or only
when the User asks?" (`assumptions.md` U7, `[HIGH]`).

The domain expert resolved this (R7): **Yes. A new Session
proactively reports on the status of Jobs submitted in previous
Sessions. This is not on-demand — it is the default behavior.**

## Decision

When a new Session begins, the `agent-interaction` module
**proactively** queries the `scheduling` module for all Jobs
belonging to the User and reports their states to the User.

### Mechanism

1. `SessionService.startSession(user)` calls
   `SchedulingService.queryJobsByUser(user.slurmUsername)`.
2. For each Job returned, the Agent identifies the associated
   Workflow (if any) and Case (if any) by querying the persisted
   Workflow state (ADR-006) and cross-referencing Job IDs.
3. The Agent presents a summary to the User:

   ```
   Welcome back. You have 3 Jobs from previous sessions:
   - Job 4827365: RUNNING (Case bhist_f09_g17_001, Workflow cesm_and_postproc)
   - Job 4827366: COMPLETED (Case bhist_f09_g17_002)
   - Job 4827367: PENDING (standalone CDO remap)
   ```

4. If SLURM is unreachable at Session start, the Agent reports:

   ```
   Welcome back. SLURM is currently unreachable. Job states from
   previous sessions are UNKNOWN. The Agent will retry with backoff
   and report states when SLURM recovers.
   ```

5. After the proactive report, the User can interact normally. The
   Agent does NOT continuously poll SLURM during the Session unless
   a Workflow is actively waiting for a Job.

### What "proactively" means

- **Proactive**: the Agent reports without being asked. The User
  does not need to say "what are my Jobs?" — the Agent tells them
  at Session start.
- **Not continuous**: the Agent does not poll SLURM every N seconds
  for the entire Session. It polls at Session start and when a
  Workflow step is waiting for a Job to complete.
- **Not on-demand only**: the original question was "proactive vs.
  on-demand." The domain expert chose proactive (R7).

### Job discovery across Sessions

Jobs are discoverable by JobID because:

1. SLURM does not cancel Jobs when the Agent's Session ends
   (INV-W4). The Jobs continue on compute nodes.
2. `squeue -u <username>` returns all active Jobs for the User,
   regardless of which Session submitted them.
3. `sacct -j <jobId>` returns historical data for Jobs that have
   completed between Sessions (used for reconciliation, FM-S2,
   R13).
4. The persisted Workflow state (ADR-006) records which Job IDs
   were submitted by which Workflow steps, enabling the Agent to
   associate Jobs with Workflows across Sessions.

## Consequences

**Positive:**
- Scientists immediately know the status of their long-running Jobs
  when they return to the Agent. This matches their mental model
  ("I started a CESM run yesterday — is it still going?").
- The Agent can suggest next steps ("Job 4827365 is COMPLETED.
  Would you like to run the post-processing Workflow?").
- The mechanism is simple: one `queryJobsByUser()` call at Session
  start, cross-referenced with persisted Workflow state.

**Negative:**
- If the User has many Jobs (hundreds of SLURM Jobs from various
  sources), the proactive report may be noisy. Mitigation: the
  Agent filters to Jobs that were submitted via cera (by
  cross-referencing persisted Workflow state and ProvenanceRecords).
- If SLURM is slow at Session start, the proactive report delays
  the Session. Mitigation: timeout after 10 seconds; if SLURM is
  slow, report "Job states are being retrieved" and continue
  asynchronously.
- The persisted Workflow state must be kept in sync with SLURM
  Job IDs. If a Workflow JSON is corrupted or deleted, the Agent
  can still report Job states (via `queryJobsByUser()`) but cannot
  associate them with Workflows.

## Alternatives

### Alternative A: On-demand Job reporting
The Agent only reports Job states when the User asks ("what are my
Jobs?"). Rejected by the domain expert (R7): the default should be
proactive.

### Alternative B: Continuous polling
The Agent polls SLURM every N seconds for the entire Session and
pushes Job state changes to the User. Rejected: excessive SLURM
load, noisy UX. The Agent polls at Session start and when a
Workflow is actively waiting.

### Alternative C: Webhook-based notifications
Use `ctx.webhookRuntime` to receive SLURM completion notifications.
The Agent registers a webhook with SLURM (if supported) and gets
pushed Job state changes. Rejected for now: SLURM's webhook/epilog
support varies and adds infrastructure complexity. Polled
`queryJobsByUser()` at Session start is sufficient. Webhooks may be
added later as an optimization.
