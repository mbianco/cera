# ADR-008: Strict exit code policy

**Status:** Accepted
**Date:** 2026-09-14
**Spec references:** `resolutions.md` R4; `assumptions.md` U3
(resolved: VALIDATED, strict default); `invariants.md` INV-T3;
`failure-modes.md` FM-T3; `features/cdo-operations.feature`

## Context

The original invariant INV-T3 stated: "A Dataset produced by a
ToolInvocation is not registered as available for downstream
consumption unless the ToolInvocation's ExitOutcome indicates
success (Exit Code 0, or a Tool-specific non-error code documented
in advance)."

This raised an open question (`assumptions.md` U3, `[HIGH]`): CDO
reportedly returns exit code 1 for some warnings (metadata
inconsistencies, non-fatal data issues). Is exit code 1 a non-error
(usable output with a warning flag), or is any non-zero exit code a
failure?

The feature file `cdo-operations.feature` included both
interpretations as scenarios, pending domain expert confirmation.

The domain expert resolved this (R4): **Any non-zero exit code
blocks output registration. The Agent does not treat non-zero exit
codes as non-errors unless the User explicitly overrides for a
specific ToolInvocation.**

## Decision

### Strict by default

Any non-zero exit code blocks output registration (INV-T3). The
output Dataset is NOT registered as available for downstream
consumption. A ProvenanceRecord is still written (recording the
non-zero exit code), but the output is not registered.

### Permissive is opt-in per ToolInvocation

The `ToolInvocationRequest` type includes an optional
`permissiveExitCodes: number[]` field. If the User explicitly lists
non-zero exit codes that should be treated as non-errors for this
specific ToolInvocation, the output is registered with a warning
flag.

```typescript
interface ToolInvocationRequest {
  // ...
  /**
   * R4 (strict exit codes): empty by default. Non-zero exit codes
   * are errors unless the User explicitly lists them here as
   * permissive for this specific ToolInvocation.
   */
  permissiveExitCodes?: number[];
}
```

### What "User explicitly overrides" means

- The User must explicitly state, for a specific ToolInvocation,
  that a non-zero exit code is acceptable.
- The override is per-invocation, not per-Tool, not per-Session,
  not global.
- The override is not inferred from context ("the User seems to
  expect warnings"). It must be explicit.
- The LLM cannot override on its own. The override comes from the
  User (via the `agent-interaction` module's `ActionRequest` →
  `ToolInvocationRequest` pipeline).

### ProvenanceRecord records the exit code regardless

Whether strict or permissive, the ProvenanceRecord always records
the actual ExitOutcome. If permissive, the record includes a flag
indicating "warning, not failure."

## Consequences

**Positive:**
- Scientific integrity: by default, only verified-success outputs
  are registered. A non-zero exit code that the User didn't
  anticipate is caught, not silently passed through.
- No "documented in advance" requirement: the original invariant
  required per-Tool success definitions to be "documented in
  advance." The strict default eliminates this requirement — 0 is
  always success, non-zero is always failure, unless the User says
  otherwise for this invocation.
- Simple mental model: "exit code 0 = success, anything else =
  failure, unless you explicitly say otherwise."

**Negative:**
- If a Tool commonly returns exit code 1 for warnings (e.g., CDO),
  the User must override on every invocation that produces
  warnings. This is deliberate: the User should be aware of
  warnings, not have them silently swallowed.
- The LLM cannot auto-detect "this is a warning, not an error" and
  proceed. This is also deliberate: for climate science,
  incorrect parameters may produce plausible-looking but wrong
  output, which is worse than a crash (FM-A2).
- The open question "do other Tools use non-zero exit codes for
  success?" (`assumptions.md` U3, extended) remains UNKNOWN but
  does not block: strict applies to all Tools by default.

## Alternatives

### Alternative A: Permissive by default for CDO
CDO's exit code 1 for warnings is a known behavior. Treat exit code
1 as non-error for CDO by default, requiring opt-out for strict.
Rejected (R4): the User should be aware of warnings. The strict
default ensures that.

### Alternative B: Per-Tool success definitions
Define a per-Tool success function: `cdo.success = (exitCode) =>
exitCode === 0 || exitCode === 1`. Rejected: requires "documented
in advance" knowledge of each Tool's exit code semantics, which is
an open question (U3, extended). The strict default avoids this
requirement.

### Alternative C: Global configuration
Allow the User to set a global "permissive mode" that applies to
all ToolInvocations. Rejected: too broad. A global permissive mode
would swallow exit codes from Tools that don't use non-zero for
success, potentially registering invalid output.
