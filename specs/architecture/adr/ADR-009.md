# ADR-009: Provenance store design — local corruption, not systemic

**Status:** Accepted
**Date:** 2026-09-14
**Spec references:** `resolutions.md` R11; `assumptions.md` L5-Q2
(resolved: local); `invariants.md` INV-P1, INV-P2; `failure-modes.md`
FM-P2; `features/provenance.feature`

## Context

The original failure mode FM-P2 (Corrupted ProvenanceRecord) had an
open blast radius question (`assumptions.md` L5-Q2): "Is one
corrupted record a local issue (quarantine that Dataset) or a
systemic issue (audit the entire Provenance store)?"

This is architecturally significant:
- **Local**: the Provenance store can be a simple append-only log
  (one file per record, or a directory of files). A corrupted record
  affects only its associated Dataset. Other Datasets with valid
  records remain available. The store does not need transactional
  integrity across records.
- **Systemic**: the Provenance store must be transactional (e.g., a
  database with ACID guarantees). A corrupted record may indicate
  systemic corruption, requiring a full audit and potentially
  shutting down all Datasets until integrity is verified.

The domain expert resolved this (R11): **A corrupted
ProvenanceRecord is a local issue. Quarantine the affected Dataset,
not the entire store. Recovery class: degradable (partial service —
other Datasets remain available).**

## Decision

### Provenance store: one file per record

The Provenance store is a **directory of JSON files**, one per
ProvenanceRecord, stored in a user-specific directory (e.g.,
`~/.cera/provenance/{provenanceRecordId}.json`). This is consistent
with the Workflow persistence model (ADR-006) and the
filesystem-based approach throughout cera.

### Why one file per record

- **Local corruption**: if one file is corrupted (partial write,
  disk error), only that record is affected. Other files
  (records for other Datasets) remain valid and available.
- **Append-only**: new records are new files. No existing file is
  ever modified (INV-P1). An atomic write (temp file + rename)
  ensures each record is either fully written or not at all.
- **Simple recovery**: to verify a single Dataset's Provenance, read
  one file. To query a lineage, follow the input Dataset
  references across files.
- **No database dependency**: consistent with the HPC environment
  (no database server required).

### Corruption handling

When `provenance.verifyProvenance(datasetId)` detects a corrupted
record (unparseable JSON, missing fields per INV-P2, or filesystem
error):

1. **Quarantine the affected Dataset** (not the entire store):
   `provenance.quarantineDataset(datasetId, reason)`. The Dataset
   is marked as quarantined and is not available for downstream
   consumption.
2. **Attempt reconstruction**: `provenance.reconstructProvenanceRecord()`
   uses available metadata (ToolInvocation logs, Environment state,
   partial record) to reconstruct the record. If reconstruction
   succeeds, the Dataset is un-quarantined and a new (corrected)
   ProvenanceRecord is written, linked to the original via a
   "corrects" relationship.
3. **Other Datasets remain available**: the rest of the Provenance
   store is not audited or shut down. Datasets with valid
   ProvenanceRecords continue to be consumable.
4. **User notification**: the User is notified that Dataset
   `{name}` is quarantined due to corrupted Provenance. If
   reconstruction fails, the User is asked to provide the missing
   Provenance information manually or regenerate the Dataset.

### What this does NOT mean

- The store is **not transactional** across records. There is no
  guarantee that a multi-Dataset ToolInvocation writes all its
  ProvenanceRecords atomically. If some records are written and
  others fail (FM-P1), the successfully written records are valid
  and their Datasets are available; the failed records' Datasets
  are held in an unregistered state.
- The store is **not audited** on corruption. A single corrupted
  record does not trigger a full-store audit. If corruption is
  widespread (multiple records corrupted), the User is notified
  and a manual audit is recommended — but this is not automatic.
- The store is **not encrypted or signed**. ProvenanceRecords are
  JSON files on the HPC filesystem. External modification is
  possible (FM-X5) but is detected via mtime/checksum mismatch,
  not prevented.

## Consequences

**Positive:**
- Simple store design: directory of JSON files, no database.
- Local corruption does not halt the entire system. Other
  Datasets remain available.
- Recovery is straightforward: read one file, attempt
  reconstruction, write a new file if successful.
- Consistent with the filesystem-based approach throughout cera
  (Provenance, Workflow state).

**Negative:**
- No cross-record transactional integrity. A multi-Dataset
  ToolInvocation may leave some records written and others not.
  Mitigation: the Agent retries failed writes with backoff
  (FM-P1) and does not register any output Datasets until all
  ProvenanceRecords are written.
- No automatic detection of systemic corruption. If the
  filesystem itself is corrupting files (hardware failure),
  individual records will be quarantined but the root cause is
  not detected by cera. Mitigation: the User is notified of
  each corruption and can investigate the filesystem.
- No built-in indexing. Querying "show me all ProvenanceRecords
  for Tool X" requires scanning all files. Mitigation: the
  query is rare (scientific audit, not performance-critical)
  and can be optimized later with an index file if needed.

## Alternatives

### Alternative A: Systemic (database with ACID)
Use SQLite or another embedded database for the Provenance store.
ACID guarantees across records. On corruption, audit the entire
store. Rejected by the domain expert (R11): corruption is local.
A database adds a binary dependency and complexity that is not
justified by the actual failure mode.

### Alternative B: Append-only log (single file)
All ProvenanceRecords are appended to a single file (like a write-
ahead log). A corrupted record in the middle of the file affects
all subsequent records (they can't be parsed past the corruption
point). Rejected: this makes corruption systemic, not local. One
file per record ensures corruption is isolated.

### Alternative C: Encrypted/signed records
Each ProvenanceRecord is signed to detect tampering. Rejected for
now: external modification is detected via mtime/checksum mismatch
(FM-X5), which is sufficient for the current threat model. Signing
adds key management complexity. Can be added later if the threat
model changes.
