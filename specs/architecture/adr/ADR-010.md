# ADR-010: LLM hallucination policy — refuse and ask

**Status:** Accepted
**Date:** 2026-09-14
**Spec references:** `resolutions.md` R12; `assumptions.md` L5-Q3
(resolved: refuse and ask); `failure-modes.md` FM-A1, FM-A2;
`cross-context/interactions.md` X10; `features/workflow-execution.feature`

## Context

The LLM (language model) at the heart of the Agent translates the
User's scientific intent, expressed in natural language, into
ToolInvocations. This translation is fallible: the LLM may
**hallucinate** Tool names ("cdo_remap" instead of "cdo
-remapcon2") or parameters (a grid file path that doesn't exist,
a variable name not in the Dataset, an incompatible operator
chain).

The original cross-context interaction X10 (C7↔C1) stated: "The
Agent must not hallucinate Tool names or parameters — if a
requested Tool or parameter is not in the Tool catalog, the Agent
asks the User for clarification rather than guessing."

However, the **recovery behavior** was an open question
(`assumptions.md` L5-Q3): "When the Agent (LLM) hallucinates a Tool
name or parameters, what is the desired behavior — refuse and ask,
or attempt best-effort?"

This is architecturally significant because it determines:
- Whether the `agent-interaction` module validates before or after
  invocation.
- Whether the module has a "best-effort" code path (try the closest
  match, or substitute parameters).
- Whether hallucinated invocations produce output (which may be
  plausible-looking but wrong — worse than a crash for climate
  science).

## Decision

**Refuse and ask.** When the LLM hallucinates a Tool name or
parameters, the Agent refuses and asks the User for clarification.
No best-effort attempts.

### Validation before invocation

The `agent-interaction` module's `validateAction()` function
performs two checks **before** creating a ToolInvocation:

1. **Tool name check**: the requested Tool name must exist in the
   Tool catalog (via `tool-invocation.getToolCatalog()`). If not,
   return `{ refuseAndAsk: true, message: "...", availableTools:
   [...] }`. The Agent presents the available Tools to the User.

2. **Parameter check**: the requested parameters must match the
   Tool's schema AND the input Dataset's metadata (via
   `data-management.queryDataset()`). If a parameter references a
   non-existent path, variable, or grid, return
   `{ valid: false, reason: "..." }`. The Agent reports the
   specific invalidity and asks the User to correct it.

### No best-effort code path

There is **no** code path in `agent-interaction` that:
- Substitutes a "close" Tool name (e.g., "cdo_remap" → "cdo
  -remapcon2").
- Infers missing parameters from context.
- Attempts the invocation with corrected parameters and shows the
  User the result, hoping it's what they meant.
- Silently drops parameters the LLM hallucinated and proceeds with
  the rest.

### Why refuse and ask

For climate science, incorrect parameters may produce
**plausible-looking but wrong** output (FM-A2). A time-mean of the
wrong variable, a remap to the wrong grid, or an aggregation over
the wrong dimension produces output that looks correct but is
scientifically invalid. This is worse than a crash:

- A crash is visible: the User knows something went wrong.
- Wrong output is invisible: the User may use it in publications,
  leading to scientific errors that are discovered months later.

The cost of asking (one extra User interaction) is far less than
the cost of wrong scientific output (retracted papers, wasted
compute, damaged reputation).

### What the User sees

**Hallucinated Tool name:**
```
The Tool "cdo_remap" is not in the catalog. Available Tools:
- cdo (CLI Tool, CDO 2.0.5)
- ncks (CLI Tool, NCO 5.1.6)
- ncra (CLI Tool, NCO 5.1.6)
- healpy_analysis (Python Tool, healpy 1.16.6)
- cesm case.submit (Model Tool, CESM 2.3.0)

Which Tool would you like to use?
```

**Hallucinated parameters:**
```
The parameters for Tool "cdo" are invalid:
- Grid file "/scratch/snx3000/cera_user/grids/nonexistent.txt" does not exist.
- Variable "TEMPERATURE" is not in Dataset "tas_historical_2000-2010" (available: TAS, PR).

Please correct the parameters and try again.
```

## Consequences

**Positive:**
- Scientific integrity: no wrong output from hallucinated Tools or
  parameters.
- Simple architecture: `validateAction()` returns valid, invalid,
  or refuseAndAsk. No best-effort code path to maintain or test.
- Clear User feedback: the User always knows what went wrong and
  what the available options are.
- Trust: the User can trust that the Agent does exactly what they
  asked, not a guess.

**Negative:**
- More User interactions: the User must clarify when the LLM
  hallucinates. This is the cost of correctness.
- No graceful degradation: if the LLM is "close" (e.g., "cdo
  remap" instead of "cdo -remapcon2"), the Agent does not try to
  interpret intent. This is deliberate: "close" is not "correct"
  in climate science.
- The LLM's capabilities are not fully utilized: some LLMs can
  suggest corrections ("did you mean cdo -remapcon2?"). The
  architecture does not leverage this, because the User should
  confirm, not the LLM.

## Alternatives

### Alternative A: Best-effort with confirmation
The Agent attempts the closest match and shows the User the result
("I ran cdo -remapcon2 instead of cdo_remap. Here's the output. Is
this what you wanted?"). Rejected: for large Datasets (TB), running
a Tool to check is expensive. And the User may not be able to tell
if the output is correct by looking at it.

### Alternative B: LLM self-correction
The Agent feeds the validation error back to the LLM and lets the
LLM correct its own output ("the Tool 'cdo_remap' doesn't exist.
Try again."). Rejected for now: this creates a feedback loop that
may amplify hallucinations rather than correct them. The User
should be the source of truth, not the LLM. (This could be
reconsidered later if LLM self-correction proves reliable.)

### Alternative C: Strict mode with override
The Agent refuses by default but allows the User to enable
"permissive mode" where the LLM can attempt corrections. Rejected:
too similar to the exit code policy (ADR-008), and the risk profile
is different. A wrong exit code produces a warning; a wrong
parameter produces wrong science. There is no safe "permissive"
mode for hallucinated parameters.
