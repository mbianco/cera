# ADR-011: FirecREST as second backend

**Status:** Accepted
**Date:** 2026-09-16
**Spec references:** `specs/firecrest/` (invariants, failure modes,
assumptions, features); `specs/architecture/adr/ADR-005.md`
(dsh isolation layer — the seam this uses)

## Context

cera currently runs on the Alps login node and invokes tools (CDO,
NCO, CESM, Python tools) via local subprocess. The dsh-adapter
module (Phase 1, ADR-005) wraps dsh's extension points into stable
cera-internal interfaces:

- `ShellExecutor.execute(command) → ShellResult`
- `SubprocessRunner.execute(command, args) → ShellResult`
- `FilesystemGateway.exists(path) → boolean`, `readFile`, `writeFile`, etc.
- `SchedulingService.submitJob(request) → Job`, `queryJob`, `cancelJob`

These interfaces are transport-agnostic. The domain modules
(environment-management, provenance, data-management,
tool-invocation, agent-interaction) depend on the interfaces, not
on the local subprocess implementation.

The domain expert wants scientists to run cera on their laptops and
access Alps HPC resources via FirecREST — CSCS's RESTful API for
HPC. This eliminates the need for SSH access, VPN connections, or
running cera on the shared login node.

## Decision

Add `src/firecrest-adapter/` as a sibling to `src/dsh-adapter/`.
Both implement the same cera-internal interfaces. The backend is
selected at startup via configuration (`--backend local|firecrest`).

### Module structure

```
src/firecrest-adapter/
├── types.ts              — FirecrestConfig, JwtTokenProvider, FirecrestError types
├── firecrest-client.ts   — Low-level HTTP client (GET, POST, PUT, DELETE with JWT)
├── shell-executor.ts     — Implements ShellExecutor by submitting Jobs (all parallel)
├── subprocess-runner.ts  — Implements SubprocessRunner by submitting Jobs
├── filesystem-gateway.ts — Implements FilesystemGateway via FirecREST filesystem endpoints
├── scheduling-service.ts — Implements SchedulingService via FirecREST compute endpoints
└── index.ts              — Barrel exports + createFirecrestBackend factory
```

### Key design decisions

1. **All ToolInvocations become parallel (F-INV-6).** FirecREST
   has no "run command and wait" endpoint. Every Tool that executes
   on the HPC is submitted as a SLURM Job via
   `POST /compute/{system}/jobs`. cera polls the Job state until
   terminal, then derives the ExitOutcome.

2. **uenv is loaded in Job scripts (F-INV-5).** FirecREST does not
   expose uenv management. cera embeds `uenv start <spec> --` in
   the Job script before the Tool command. The EnvironmentService
   interface is NOT used by the FirecREST backend.

3. **Provenance stays on the HPC (F-INV-7).** ProvenanceRecords are
   written via FirecREST filesystem endpoints
   (`POST /filesystem/{system}/ops/upload` for ≤5MB,
   `POST /filesystem/{system}/transfer/upload` for >5MB). The
   Provenance store path remains on the HPC filesystem.

4. **JWT token management.** A `JwtTokenProvider` interface
   abstracts token acquisition and refresh. The default
   implementation uses the OIDC client credentials grant. On 401,
   cera refreshes the token and retries. On persistent auth
   failure, the User is notified.

5. **File size awareness.** Before any file transfer, cera stats
   the file via `GET /filesystem/{system}/stat/{path}`. Files
   ≤5MB use synchronous `/ops/...` endpoints. Files >5MB use
   asynchronous `/transfer/...` endpoints (submit + poll).

6. **No modification to existing modules.** The FirecREST adapter
   is purely additive. The local (dsh) backend remains for
   development, testing, and scientists who prefer the login node.
   No existing source file is changed (except `src/index.ts` for
   the barrel export).

## Consequences

**Positive:**
- Scientists can run cera on their laptops — better LLM latency,
  no shared login-node constraints, no SSH/VPN setup
- The dsh-adapter isolation layer (ADR-005) is validated — this is
  exactly the change it was designed for
- OIDC authentication is simpler and more secure than SSH keys
- Running Jobs on the HPC are not affected by FirecREST outages
  (FM-F-4 — same as FM-S2 for the local backend)
- ADR-004 (SLURM-only) is unchanged — FirecREST is a transport,
  not a different scheduler

**Negative:**
- All ToolInvocations become parallel — a 2-second CDO command
  becomes a 30-second Job (F-A-1)
- File access latency is higher (HTTP vs direct filesystem, F-A-3)
- uenv cannot be verified before Job submission (F-A-2) — the Job
  may fail if the uenv doesn't exist (FM-F-9)
- Large file transfers are asynchronous and require polling (F-INV-4)
- New failure modes (FM-F-1 through FM-F-9) that don't exist in the
  local backend

## Alternatives

### Alternative A: Apptainer (Singularity) image
Bundle cera + Node.js + all deps into an Apptainer image. Run on
the login node (or via `apptainer run` from a laptop with SSH).
**Rejected:** Contradicts the uenv philosophy (uenv provides the
runtime), adds container management overhead, and still requires
SSH access to the login node — the exact thing FirecREST eliminates.

### Alternative B: Single-file bundle (esbuild/tsdown with deps inlined)
Bundle everything into a single JavaScript file. Download to the
laptop and run with `node cera.bundle.js`.
**Rejected:** dsh's plugin architecture requires dynamic
`require()` at runtime. Bundling breaks this. Also, no `npm update`
path — every update requires a new bundle.

### Alternative C: Replace dsh-adapter entirely
Remove the local subprocess backend and make FirecREST the only
backend.
**Rejected:** The local backend is essential for development and
testing. Scientists who prefer the login node should not be forced
to use FirecREST. The additive approach is lower risk.
