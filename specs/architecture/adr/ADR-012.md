# ADR-012: FirecREST is the only production HPC transport

**Status:** Accepted
**Date:** 2026-09-17
**Supersedes:** ADR-011 (FirecREST as second backend) — ADR-011 is NOT
deleted (append-only). ADR-011's analysis remains valid for the
dev-mode local backend. This ADR records that the local backend is
**not** a production path.
**Spec references:** `resolutions-r14.md` R14.1–R14.7;
`specs/firecrest/invariants.md` F-INV-1 through F-INV-7 (elevated to
primary); `specs/firecrest/failure-modes.md` FM-F-1 through FM-F-9
(production failure modes); `specs/firecrest/assumptions.md` F-A-1
through F-A-4; `specs/invariants-firecrest-primary.md`;
`specs/failure-modes-firecrest-primary.md`; `specs/impact-analysis.md`;
`specs/architecture/adr/ADR-003.md` (uenv — re-evaluated);
`specs/architecture/adr/ADR-005.md` (dsh isolation — unchanged for dev);
`specs/architecture/adr/ADR-011.md` (superseded)

## Context

ADR-011 (accepted 2026-09-16) introduced FirecREST as a **second**
backend alongside the local (dsh-adapter) backend. ADR-011 point 6
claimed "No modification to existing modules" — the FirecREST adapter
was described as "purely additive." Finding FCREST-01 demonstrated that
this claim is false: F-INV-5 and F-INV-6 require behavioral changes in
`tool-invocation` and `environment-management`, both existing modules
with fully implemented source code (Phase 4, 133 tests; Phase 2, 239
tests respectively).

The domain expert has now made a stronger architectural decision:
**FirecREST is the only supported HPC transport.** The local backend is
demoted to a dev-only mode (`--backend dev`) for testing without a real
FirecREST instance. The key implications are:

1. **dsh runs on the laptop** (R14.1). The agent loop, LLM adapter,
   session management, and tool registration all happen locally. The
   scientist talks to the LLM directly on their machine.

2. **FirecREST is the only production HPC transport** (R14.2). All HPC
   operations — Job submission, Job state query, Job cancellation, file
   listing, file read/write, file stat, directory creation — go through
   FirecREST's REST API. No SSH, no VPN, no login-node subprocess.

3. **uenv is always loaded in Job scripts** (R14.3). The
   EnvironmentService interface (uenv mount/unmount, verifyEnvironment,
   checkUenvAvailability, detectConflicts) is removed from the
   production path. cera embeds `uenv start <spec> --` in the Job
   script submitted via FirecREST. The Environment types
   (Environment, UenvSpec, Module, Conflict) stay and are used by
   `tool-invocation` to construct Job scripts.

4. **All ToolInvocations are parallel** (R14.4). The `executionModel:
   'synchronous'` field is ignored in production. Every Tool that
   executes on the HPC is submitted as a SLURM Job via FirecREST.
   cera polls the Job state until terminal, then derives the
   ExitOutcome.

5. **Local backend is dev-only** (R14.5). The dsh-adapter (wrapping
   local subprocess for ShellExecutor, SubprocessRunner,
   FilesystemGateway) is for testing only. It is not a production path
   and must not be documented as such.

6. **SLURM CLI scheduling is dev-only** (R14.6). The scheduling module's
   CLI implementation (sbatch, squeue, scancel via SubprocessRunner) is
   replaced by FirecRESTSchedulingService in production. The
   SchedulingService interface stays.

7. **`--backend` defaults to `firecrest`** (R14.7).

## Decision

FirecREST is the only production HPC transport. The `--backend` flag
defaults to `firecrest`. The `--backend dev` flag selects the local
dsh-adapter for development and testing only.

### Key design decisions

1. **FirecREST is the default and only production backend.** The
   `--backend` flag defaults to `firecrest`. The `firecrest-adapter`
   module provides ShellExecutor, SubprocessRunner, FilesystemGateway,
   and SchedulingService implementations via FirecREST REST API.
   Domain modules receive these interfaces at startup and never see
   the FirecREST HTTP client or JWT token.

2. **`tool-invocation` is modified for production.** Under R14, the
   `invokeTool()` flow no longer calls `EnvironmentService` (which is
   absent in production). Instead, the Job script is constructed with
   `uenv start <spec> --` embedded before the Tool command. The
   `executionModel` field is ignored in production — all
   ToolInvocations are submitted as SLURM Jobs. A default
   `ResourceRequest` is supplied for formerly-synchronous
   ToolInvocations that have no `resourceRequest` (resolves FCREST-05).
   See `impact-analysis.md` §6 for details.

3. **`environment-management` runtime service is dev-only.** The
   domain types (Environment, UenvSpec, Module, Conflict) stay and are
   used by `tool-invocation` to construct Job scripts. The runtime
   service implementation (environment-service.ts, uenv-parser.ts,
   conflict-detector.ts) — which calls uenv CLI commands via
   SubprocessRunner — is dev-only. In production, the Environment is
   loaded inside the Job via `uenv start <spec> --`.
   See `impact-analysis.md` §3 for details.

4. **`scheduling` CLI implementation is dev-only.** The
   SchedulingService interface stays. In production, it is implemented
   by `FirecRESTSchedulingService` (via FirecREST compute endpoints).
   In dev mode, it is implemented by the SLURM CLI
   (sbatch/squeue/scancel via SubprocessRunner).
   See `impact-analysis.md` §2 for details.

5. **`dsh-adapter` remains for dev mode.** The dsh isolation layer
   (ADR-005) is unchanged. The dsh-adapter wraps dsh's volatile
   extension points into stable cera-internal interfaces. In dev mode,
   these interfaces are backed by local subprocess. In production,
   they are backed by the FirecREST adapter. No domain module imports
   dsh directly — they always go through the adapter interfaces.
   See `impact-analysis.md` §1 for details.

6. **Provenance stays on the HPC** (F-INV-7, unchanged). ProvenanceRecords
   are written and read via FirecREST filesystem endpoints. The
   Provenance store path remains on the HPC filesystem. INV-P1
   (immutability) and INV-P4 (survives Session end) are unchanged.

## Consequences

**Positive:**
- Single production code path — no ambiguity about which backend is
  "real." Scientists get one consistent experience.
- The `tool-invocation` module is honestly modified to support the
  FirecREST-only flow, rather than pretending the FirecREST adapter is
  "purely additive" (ADR-011 point 6 was false — see FCREST-01).
- Better LLM latency (laptop vs shared login node).
- No SSH keys, no VPN, no login-node resource constraints in
  production.
- OIDC authentication (JWT) is simpler and more secure than SSH keys.
- Running Jobs on the HPC are not affected by laptop or FirecREST
  outages (FM-F-4 — same as FM-S2 for the local backend).
- The dsh-adapter isolation layer (ADR-005) is validated — the
  production backend swap demonstrates the seam works.

**Negative:**
- All ToolInvocations become parallel — a 2-second CDO command becomes
  a 30-second Job (submission + queue + execution + polling). This is
  the trade-off for running cera on a laptop (F-A-1, now a primary
  assumption).
- uenv cannot be verified before Job submission (F-A-2). The Job may
  fail if the uenv doesn't exist (FM-F-9). This is accepted — the
  failure is clear and recoverable.
- File access latency is higher (HTTP vs direct filesystem, F-A-3).
- Large file transfers are asynchronous and require polling (F-INV-4).
- New failure modes (FM-F-1 through FM-F-9) that don't exist in the
  local backend.
- The `environment-management` module's runtime service is split
  between production (types used by tool-invocation) and dev (runtime
  uenv CLI commands). This creates a conceptual split that must be
  clearly documented.
- Tests must be reclassified: production tests use FirecREST mocks;
  dev tests use local subprocess mocks. No tests are removed — they
  are reclassified. See `impact-analysis.md` for per-module details.
- `tool-invocation` requires modification: the `invokeTool()` flow must
  handle the absence of `EnvironmentService` and the universal parallel
  execution model. Finding FCREST-01 is resolved by this ADR.

**What changes in the codebase:**
- `tool-invocation`: `invokeTool()` modified to (a) skip
  `EnvironmentService` when absent, (b) embed `uenv start <spec> --` in
  Job scripts, (c) always use the parallel execution path in
  production, (d) supply a default `ResourceRequest` for
  formerly-synchronous ToolInvocations.
- `environment-management`: runtime service (environment-service.ts,
  uenv-parser.ts, conflict-detector.ts) tagged as dev-only. Domain
  types (Environment, UenvSpec, Module, Conflict) remain and are
  exported for use by `tool-invocation`.
- `scheduling`: SLURM CLI implementation tagged as dev-only.
  `FirecRESTSchedulingService` is the production implementation.
  `SchedulingService` interface unchanged.
- `dsh-adapter`: tagged as dev-only backend. Interfaces unchanged.
- `provenance`: implementation updated to use FirecREST filesystem
  gateway in production (already done in FCREST phases per F-INV-7).
- `data-management`: implementation updated to use FirecREST filesystem
  gateway in production (already done in FCREST phases).
- `agent-interaction`: `reportJobStatus()` updated to use
  `FirecRESTSchedulingService.queryJobsByUser()` in production (already
  done in FCREST phases).
- `src/index.ts` or startup code: `--backend` defaults to `firecrest`.

**What stays the same:**
- All domain types (Dataset, Tool, ToolInvocation, Job, Environment,
  ProvenanceRecord, Session, Workflow, Experiment, Action, etc.).
- All bounded contexts (C1–C7) and their consistency boundaries.
- The dsh isolation layer (ADR-005) — dsh-adapter wraps dsh, no other
  module imports dsh directly.
- All invariants that are UNCHANGED (see
  `invariants-firecrest-primary.md` for the full classification).
- All Gherkin features that describe domain behavior (not transport
  specifics).
- The test suite structure (742 tests across 7 modules) — tests are
  reclassified, not removed.

**Which tests are affected:**
- See `impact-analysis.md` for per-module test impact. Summary:
  - Tests that exercise `EnvironmentService` runtime operations
    (loadUenv, verifyEnvironment, checkUenvAvailability,
    detectConflicts) → tagged as `@dev-only`.
  - Tests that exercise synchronous `executionModel` dispatch → tagged
    as `@dev-only`.
  - Tests that exercise local SLURM CLI (sbatch/squeue/scancel) →
    tagged as `@dev-only`.
  - Tests that exercise local FilesystemGateway (exists, readFile,
    writeFile via local fs) → tagged as `@dev-only` for file I/O
    tests; domain logic tests (Dataset immutability, format/grid
    validation) remain production.
  - Tests that exercise FirecREST endpoints → tagged as `@production`
    (already present from FCREST phases).
  - Tests that exercise domain logic through mocked interfaces →
    remain unchanged (interface-level tests are transport-agnostic).

## Alternatives

### Alternative A: Keep both backends as production (ADR-011 unchanged)

Maintain both the local backend and the FirecREST backend as
production options. Scientists can choose `--backend local` or
`--backend firecrest`.

**Rejected.** The domain expert has decided that FirecREST is the only
production transport. Maintaining two production code paths is
confusing, creates a testing burden (every feature must work on both
backends), and makes it unclear which backend is "canonical." The
local backend's `EnvironmentService` (which runs uenv CLI commands on
the login node) is fundamentally incompatible with the FirecREST
architecture (where cera runs on a laptop). The "purely additive"
framing of ADR-011 was false (FCREST-01) — maintaining the fiction
blocks honest engineering.

### Alternative B: Remove the local backend entirely

Delete the dsh-adapter module and all local backend code. FirecREST
is the only backend.

**Rejected.** The local backend is essential for development and
testing. Running the full test suite against a real FirecREST instance
is expensive, slow, and not always available (e.g., CI, offline
development). The dsh-adapter provides a fast, local way to test
domain logic without HPC access. The types (ShellExecutor,
SubprocessRunner, FilesystemGateway, SchedulingService) are
transport-agnostic and must be tested with a local implementation.

### Alternative C: Abstract over backends with a strategy pattern

Introduce a `BackendStrategy` interface in `tool-invocation` that
selects execution behavior based on the active backend. The strategy
is injected at startup; `tool-invocation` calls the strategy instead of
dispatching on `executionModel` directly.

**Partially adopted.** The backend selection at startup (via
`--backend` flag) is a form of strategy selection. However, the domain
expert's decision is simpler: in production, all ToolInvocations are
parallel and uenv is in Job scripts. There is no need for a
per-invocation strategy — the backend is selected once at startup, and
the production behavior is fixed. The `tool-invocation` module is
modified to support both modes (production: always parallel, uenv in
Job scripts; dev: dispatch on executionModel, EnvironmentService
optional). This is simpler than a full strategy pattern and matches
the domain expert's intent.
